# Personal Agent engineering guide

- Read the relevant sections of `docs/development/architecture.md` and the owning plugin README before changing a boundary. Each module owns one responsibility; use targeted reads instead of repeatedly loading unrelated modules.
- `kernel/` and the public `api/` contracts use only the standard library and kernel contracts. Never import plugins there; version range policy and package inspection belong to `app/`.
- Keep Pi protocol fields inside `core/pi/`; the kernel owns only provider-neutral execution contracts. Pi is the sole agent loop. Voice is disabled pending independent acceptance.
- Add a capability contract and an adapter for a new device/provider. Do not add hardware branches to the assistant.
- Before changing go2rtc deployment or adding cameras through it, read `docs/guides/cameras.md` for device mapping, stable identity, permissions, reconnection and acceptance.
- Model failures never select alternative models or replay uncertain tool operations. Bounded request retries use Pi's public retry helper, with per-attempt durable admission and settlement; do not enable nested SDK or Agent retries. No raw recording by default, automatic room fallback, or extra audio gain.
- Wake word, assistant display name, output names and hardware identities are instance configuration.
- Main voice input/output are frozen startup bindings (`input_device` / `default_output`). Never switch them through MCP, CLI, voice commands, saved state or shell during a process. Extra audio/video endpoints are device tools; adding or using them must not replace the main voice route. Change bindings through instance configuration and restart only.
- Device streams open through `audio_inputs` / `audio_outputs` resource registries, including the fixed voice streams. Sharing is adapter-declared; default to busy, never preempt another owner. Device tool actions use typed requests and `device_operations` IDs/query/cancel; tool input is data and never an implicit user turn.
- Third-party MCP definitions belong to the integrations plugin's revisioned private `config/mcp/servers.json` registry. Store only non-secret definitions; credentials use environment references or the provider credential store. Packages, verification receipts and runtime files remain in ignored instance storage. Native provider mapping/authentication stays in its adapter; never edit global agent configuration or proxy arbitrary external tools through device MCP. Background management requires the active task's `mcp_management` resource. Saved, verified and applied are distinct; main refresh waits for idle voice/turn and never replays work.
- Event notifications must not wait for device reconnect, model inference, or memory retrieval.
- Track background work and resource cleanup through plugin contexts. Never replay uncertain user tasks.
- Memory uses upstream Mem0 with local embeddings and source validation. Extraction uses an explicitly configured, accepted `model_api.memory` binding through models; never run an extraction agent. Do not create a second live vector database or custom extraction/dedup/ranking algorithm.
- Before changing memory capture, test source validation, corrections, deletion, stale jobs and retries.
- A passing fake test does not establish real-device success. Record integration evidence separately.
- Before implementation, bound the requested behavior, reuse existing paths, and select the smallest checks covering changed contracts and their direct callers. A small feature must not automatically become a framework redesign or release exercise. Reassess scope and the critical path if routine work exceeds about ten minutes; explain a concrete blocker or necessary expansion instead of adding precautionary work. This checkpoint is not permission to skip relevant checks or stop unfinished work.
- For routine changes, run applicable static checks and affected module/class/method tests, plus focused browser verification for changed interactions. Use `scripts/check.py --test test_integrations.AdapterTest`, `--group`, `--list`, and `--static-only` as appropriate. Documentation-only changes need content/link/command review. Build `frontend/` only when its inputs change; configuration-console static assets do not require the separate chat frontend build.
- Commit/push and updating an editable development instance do not by themselves require a full suite or wheel acceptance. Run the full suite for formal releases, explicit requests, or broad shared-contract changes whose impact cannot be bounded by targeted checks; state the reason before expanding verification. Run installed-package acceptance when packaging/dependencies/installation behavior changes or delivering a formal installed release. Preserve successful evidence while the relevant inputs are unchanged; do not repeat the same acceptance in source and wheel environments without a packaging-specific reason. Report selected checks as selected, never as a full gate. All code uses one `.venv`.
- Test concurrency uses independent module processes (default up to 3; `--jobs 1` for serial diagnosis). Keep temporary state, databases and ports private; serialize modules sharing a real resource. Physical-device, authenticated-provider and installed-service acceptance scripts stay explicit and are never added to automatic parallel tests. Preserve real engine/restart/cancellation tests; speed must not come from replacing them with mocks or hiding skips/failures.
- Isolate a timing-sensitive failure to its failing module before rerunning broad checks. Record unrelated failures separately with evidence; do not automatically rerun the entire suite serially or expand the feature into unrelated repairs. Newly introduced or unresolved relevant failures still block delivery.
- For uncertain provider behavior, run a minimal isolated protocol probe early. Define the integration's acceptance boundaries before expanding implementation. Separate local checks, real-provider acceptance and deployment/user/device waits; do not rerun successful checks merely while waiting for unrelated work.
- Private instance configuration lives in ignored `config/`; reusable templates live in `config.example/`. The entry `config/config.toml` explicitly includes fragments; only `Config.load()` composes them. No recursive includes or silent overrides. Preserve the instance `root` when moving configuration: `.env`, `state/` and `models/` stay there. Never commit credentials or recordings.
- `.agents/` (and `.agent/`) is ignored local Coding AI tooling, never assistant runtime input. Keep root `AGENTS.md` tracked as the engineering guide. Bundled assistant operational skills belong to their owning plugin’s `skills/` and ship in its package; the composition root selects enabled owners. Instance skills live privately in `config/skills/`, loaded only through explicit `instance_skills` names. Instance MCP/source registries live in private `config/`; only reusable empty examples belong in `config.example/`. Runtime agents must not auto-discover project instructions, skills or extensions. User facts continue through existing memory, not a second knowledge store.
- Development has one current API/CLI. Do not add compatibility aliases. Git restores source only; runtime rollback requires matching code, dependencies and a verified stopped-instance backup. Never remove or edit release-state records to bypass downgrade protection.
- Continue development on `main` by default; leave this workspace on `main` after merging and pushing.
- Keep `scripts/` for reusable setup, checks and hardware acceptance. One-off probes/experiments belong in ignored instance storage or `/tmp`, not the source tree. Generate a report only when requested by the user.
- Keep OS mechanisms in `platforms/` or explicitly platform-specific hardware adapters. Business plugins use public `api.system` facilities; independent plugins declare the `system_io` resource. Never substitute POSIX mode assertions for Windows ACL checks, or claim Windows readiness from Linux mocks. Native acceptance commands live in `docs/development/testing.md`; dated results and pending SCM/reboot checks live in `docs/archive/platform-acceptance-2026-10.md`.

- Runtime foreground/background agents use registered `workfiles` scratch/artifact areas. Task state belongs to the tasks plugin; provider protocol stays in the Pi adapter; tasks owns goal policy and completion. Never steer a background task through the foreground turn or infer completion from memory.

- Model API configuration belongs to `model_api`; `core/models` owns no-tool inference and receipts, `core/pi` owns execution, and tasks owns policy, authorization and result delivery ownership. All model routes reuse the pinned Pi provider library; custom endpoints use explicit protocol adapters. Do not add a second agent loop, provider emulation, implicit fallback or recursive inference tools. Ordinary execution uses full local permissions. Controlled ExecutionControl contexts use the explicit Windows fixed-command/file broker; other isolation backends and arbitrary toolchains remain unsupported. Speech remains pending independent acceptance. Never infer isolation from Job ownership or ordinary execution. Real-provider parity must precede production migration; synthetic tests do not establish provider equivalence.
- Configuration and execution state have one current format. The slim/standard consolidation preserves current dialogues, tasks, notifications, evidence and credentials; use the explicit prepare-config candidate and additive execution links, never a state reset for this transition. Unknown single executions are not replayed; tasks owns validated continuation policy. Deploy only after reviewing in-flight operations and backing up the stopped instance. Tests must target current behavior rather than compatibility hooks.

- Public webpage lookup belongs to `plugins/search` behind SearchRequest/MCP/CLI. Search provider selection is independent of execution models; Pi exposes configured search providers, without an implicit subscription search fallback. Keep provider protocols, HTTP/cache limits and private metadata receipts in that plugin. Never treat page content as instructions or enable media acquisition through search.

- AI-service calls (Pi, auxiliary models/memory, Jev, paid search) must pass `core/ai_usage` durable admission before dispatch. The plugin owns policy/config/ledger; Pi owns protocol transport, tasks owns work identity/lifecycle/notification rights. Preserve one shared work allowance across children, continuation and restart. Missing token telemetry is not business failure; unknown operations must never replay. Metering failure blocks paid dispatch, not devices/events/web. Nested SDK/Agent retries and cache warming remain disabled. The Pi adapter owns the single bounded request-retry path; each attempt requires usage admission and settlement, the original deadline and work allowance. Partial output or uncertain operations forbid automatic regeneration. Keep real runaway-loop, compaction, mixed-identity and reservation tests. Execution authorization is a separate future responsibility.
- Native model accounts reuse the pinned Pi provider library and locked credential store through `core/pi/accounts.*`; they never start a second agent loop. Models owns account/provider/model declarations; the Pi adapter owns native auth and streaming. Never copy global Coding AI/Codex tokens or rotate duplicated refresh tokens. Operator-only login uses isolated `state/model-accounts/`; no model tool receives credentials or login actions. Account routes must retain usage admission, cancellation and no-replay behavior. Subscription request limits differ from API keys: unsupported output caps require explicit `output_limit="model"` and conservative native catalog reservations, not silent parameter dropping or a claim of enforced caps. Catalog/login success never establishes model capability acceptance.

- New extensions import only `assistant_runtime.api`, declare an installed package
  entry point in `personal_agent.plugins`, and accept PluginContext rather than
  the application host. Do not add another arbitrary module-factory loader.
- New or changed tools follow `docs/development/plugins.md#工具适配要求与检查边界`: keep Schema and valid `examples` with the owner, declare actual boolean behavior hints, and use public `ToolFailure` for owner-confirmed outcomes. Validate before side effects; arbitrary handler/transport exceptions are unknown, never evidence that an operation was not dispatched. Do not mutate registered Schema dictionaries or add a plugin-specific discovery/retry layer.
- Keep development quality checks strict without making optional metadata a runtime gate: missing descriptions/hints and invalid examples warn and use the shared conservative defaults. Never relax authorization, guess business arguments, silently reinterpret validation constraints, or replay unknown operations to make a tool appear compatible.
- Before changing release metadata or plugin compatibility, read `docs/development/release.md` and `docs/development/plugins.md`. `src/assistant_runtime/VERSION` is the single core/package version source; core plugins use the `core` marker. Each extension owns one static `plugin.json` with its version, bounded core compatibility, API, dependencies and platform declarations. Runtime manifests must derive from that descriptor; do not recreate default versions in plugin instances. External plugin versions match their distribution. Never widen compatibility merely to pass checks.
- Release declarations are checked by `scripts/check.py`; also run `scripts/check_release.py --wheel <candidate>` against the actual framework wheel before release. `pa upgrade-check` is read-only metadata preflight, not dependency installation or migration/device/provider acceptance. Code changes require an explicit restart; configuration revision and live updates are separate.
- Kernel dependency failures must block dependent startup and remove partial
  registrations. Test owner shutdown, cancellation and stale results.
- Work directly in the current project checkout by default. Do not create source copies or worktrees unless a major change requires isolation. Preserve the running instance during development. Before an authorized cutover, complete the risk-appropriate checks above and preserve in-flight work and required backups. A formal production release requires the full gate and package acceptance; an editable development-instance update uses targeted checks and live readiness verification.
