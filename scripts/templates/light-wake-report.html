够不够轻，够不够快？

CPU 是持续按真实时间送入音频时的进程用量。

这里以六核总容量为 100%，单核满载约 16.7%。Qwen 的低静音 CPU 来自 VAD 门控、ASR 没有执行，不能据此认为 Qwen 比小模型更轻。内存包含 Python 与推理库；不含当前助手其他进程。

20ms 与 80ms 分块

单次计算耗时与唤醒延迟不同。FSMN 需要约 260ms 右侧音频上下文，另有声学窗、输入分块和分数判定的等待；CPU 算得快，不表示说话一结束就立即触发。

独立复测：静音和真人语音

每种分块在新的进程中再跑 60 秒静音、60 秒真人音频。CPU 会随运行条件波动；同一模型不同阈值的消耗差异不能归因于阈值本身。表中保留原始实测值，不包装成固定消耗承诺。

按真实时间喂音频：同一录音何时触发

时间从录音文件开头算起，录音前部包含提示音和等待。尚未标注每个唤醒词的精确结束点，所以没有把这些数值冒充“词说完后的延迟”。

展开：完整资源与计时口径

本轮新模型静音实测为 180s / 60s，属于短时常驻测试，未做 24h 长稳。旧模型 CPU 数据来自前次同机测试，静音时长各不相同。计时器包含测量线程的少量开销，宿主其他服务持续运行。* 真人语音 CPU 预算 = 离线处理这些音频实际消耗的 CPU 秒数 ÷ 音频秒数 ÷ 六核容量，用于估计以实时速度持续送入这些样本的负载。

复用官方 WeKWS 网络及损失函数、FunASR 预训练 FSMN、Kokoro 本地合成与 ONNX Runtime。训练与验证按声线分开；之前合成测试的四个声线也全部排除在新训练之外。

MDTC-small

从头训练 60 轮；选择独立验证集较好的第 56 轮。使用响度、轻微混响、白噪声与特征遮挡增强。共 35,073 参数，最终未通过真人验收。

FSMN

从通用预训练模型继续训练 20 轮；根据合成验证集 CTC 损失选出模型。随后在持续音频输入下校准检测阈值，输出仅用于判断关键词，不走通用转写任务链。

展开：模型导出和流式正确性

该模型的官方词典把“嘟”映射到同音的“督”声学符号，未手工把“读读”加入有效触发词。CTC 解码复用已安装 FunASR 的前缀搜索，通过实验用 NumPy 适配器运行；推理进程不加载 Torch。第一轮采用实验适配器；正式 V2 已将上游推理解码器与许可证纳入插件，并增加有界缓存。

结论的边界，以及下一步

本轮可以确认

  • 轻量专用唤醒模型确实可以提升这批真人录音的命中率。
  • 预训练后定制，比仅用合成数据从头训练小网络更适合当前数据。
  • 语音模型本体很小，推理进程可以远小于完整 ASR 框架。

尚未证明

  • 不同日期、说话方式和位置都能稳定命中。
  • 全天使用时几乎没有误唤醒。
  • 这批录音上的优势能直接变成现场体验优势。
