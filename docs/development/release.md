# 发布与切换

日常升级步骤见[日常维护](../guides/operations.md)。本页用于发布包交付、配置迁移及生产切换；历史私有实例参数不作为发布默认值。

## 版本规则

版本变更及历史适配说明见[0.4 发布历史](../archive/release-history-0.4.md)。本页只维护当前版本规则与发布流程。

`src/assistant_runtime/VERSION` 是内核版本的唯一来源，Python 包、CLI 和全部核心插件共用它。当前开发候选为 `0.4.26`（API 2）；扩展分别在自己的 `plugin.json` 维护版本，仍随同一个框架 wheel 交付。内核与扩展分类保持不变。

使用稳定的 `主.次.修订` 版本，首轮不发布预发行版本。`0.x` 阶段修订号用于兼容修复及可选的兼容新增能力（例如 0.4.14、0.4.17）；次版本可引入不兼容变化，插件通常声明 `>=0.4.0,<0.5.0`。进入 `1.x` 后，兼容新增功能递增次版本，不兼容变化递增主版本。已发布版本不得覆盖重发；兼容范围须经验证维护，不能为了通过检查自动放宽。

公共插件协议 `api_version` 是内部硬性检查，独立于业务发布号；仅在公共接口发生不兼容变化时递增。配置修订摘要、描述文件 `schema_version`、模块自己的数据迁移版本不是软件版本，不能混用。

发布前更新需要变化的插件版本／兼容范围，运行全量门禁，再用 `python scripts/check_release.py --wheel <目标wheel>` 检查实际包与源码声明一致。该检查覆盖核心版本来源、全部插件的版本依赖、平台声明文件和外部示例；不能代替安装包和真实供应商验收。

### 一次变更应修改什么

| 变更 | 开发者需要维护的内容 |
| --- | --- |
| 内核或核心插件修改并发布 | 修改 `src/assistant_runtime/VERSION`；核心插件继续使用 `core` 标记，不逐个写数字版本 |
| 仓库内扩展修改或调整支持声明 | 递增该扩展 `plugin.json` 的版本；随框架 wheel 交付时同时发布新的内核／包版本，避免同版包内容变化 |
| 独立扩展修改 | 同步更新其 `plugin.json` 与 distribution 版本，二者完全一致；同一发行包内多个插件同步版本 |
| 支持新的内核版本 | 验证后更新 `requires_core`，必要时更新依赖范围；只更新实际受影响的扩展，不批量扩大范围 |
| 公共 API 不兼容变更 | 同步修改 `kernel/events.py` 的 `API_VERSION`、`release.json` 的 `api_version` 及适配后插件的声明；同时按规则发布不兼容的内核版本 |
| 持久化格式变化 | 提供所属模块迁移及备份／回滚验证；需要阻断旧格式时更新 `release.json` 的 `data_format`，仅修改代号不会执行迁移 |
| 配置值变化 | 使用配置服务生成修订，不修改软件版本或版本保护记录 |

`plugin.json` 的依赖指向插件 ID 与其发布版本；Python／Node 包依赖仍由各自包管理和锁文件处理。更改宿主依赖后更新并检查 `uv.lock`。`configuration.json` 的描述格式版本和实例的配置修订摘要均不是插件发布版本。

软件版本变化后，检查所有内置扩展及示例的兼容范围；尤其跨 `0.x` 次版本时，原范围通常应阻断新内核，须完成适配再声明支持。不要为绕过数据保护把版本号降低，也不要覆盖已发布的同版本构建。

## 1. 准备候选

记录代码提交、依赖锁文件和配置版本。在私有候选目录保留原实例 `root`、凭据引用、注册表和用途绑定，不用空模板覆盖已有配置。

使用 `pa --config <配置文件> upgrade-check <目标wheel> [--plugin-wheel <扩展wheel>]` 检查实际候选；参数可重复指定独立扩展，不能替换目标包自带插件。检查离线读取 wheel，不导入候选代码、不安装、不重启。输出目标版本、已启用插件阻断项、版本变化、wheel SHA256、数据格式状态和后续步骤。同包升级按整个 distribution 替换插件清单：新包删除了仍启用的插件会被阻断；其他已安装包提供的同名插件也会造成冲突。退出码 0 表示声明兼容，2 表示有阻断项，1 表示输入／包无效。安装依赖解析、配置语义及模块数据迁移仍需在隔离候选环境验证。

旧配置可用 `pa --config <旧配置> prepare-config <候选目录>` 生成可审查候选。核对 `conversation`、`cli` 及其依赖；Windows 默认使用 slim，只启用声明支持 Windows 的插件；standard 能否启用由所含插件的实际认证决定。模型、任务和记忆只配置实际启用的用途，不隐式启用供应商或回退。

在应用目录使用当前 `.venv` 的 Python 预检：

```sh
python -m scripts.check_pi_release --config /private/candidate/config.toml
python -m scripts.verify_integrations
```

预检检查本地配置、凭据引用、注册表、技能和 Pi 版本，不证明账号有额度、供应商可用或设备已验收。

## 2. 验证实际启用的能力

最终代码、测试和依赖修改后运行[开发检查](testing.md)。真实供应商检查使用授权的账号和费用范围、独立临时实例及明确请求上限：

```sh
python -m scripts.verify_models --config /private/test/config.toml \
  --model ACCEPTED_ALIAS --case tools --max-requests 3 \
  --max-output-tokens 1024 --confirm-paid --output /private/tools.json
```

按需检查 `text`、`image`、`memory`；任务委派使用 `scripts.verify_pi_host` 的显式主／任务模型和请求上限。只记录实际通过的用途，不将模型目录、登录成功或本地合成测试当作供应商验收。

隔离网关测试使用独立实例 root、私有鉴权、回环端口和 Docker 项目。准备工具会写入指定 root 的网关文件，不能用生产 root 生成测试配置。OAuth 轮换令牌不复制到测试实例。

## 3. 构建与安装

按[wheel 交付](../reference/installation.md#wheel-交付)导出锁定依赖并构建。确保构建目录没有遗留旧模块，检查包内的配置模板、平台声明、技能、Pi 资源，以及 standard 所需前端产物；不得包含私有实例文件。

构建后使用开发环境的 Python 执行 `python scripts/check_release.py --wheel <框架wheel>`，再把该 wheel 安装到独立验收环境。使用安装包运行原生临时验收，记录提交、包摘要、配置修订、通过／跳过／错误及实测边界。源码通过不代表安装包通过；未提交候选也不作为已发布版本。

## 4. 切换运行实例

1. 核对在途工作、未知执行和外部操作回执，明确完成或停止策略。
2. 停止后台并确认所属工具收尾，备份完整实例、原代码／环境版本和服务登记。
3. 安装审查后的包和配置，保持实例 root 与数据；不要并行启动新旧两个业务实例。
4. 网关需要变更时显式更新原网关并检查鉴权健康。Python／Node 或服务入口变化时重新登记服务。
5. 在实际服务账号及环境下检查 `pa models check`、`pa model-accounts status --account NAME`，再启动。
6. 确认配置页、CLI 和实际启用的网页、任务、MCP、记忆等能力；完成工作后再验证一次正常重启。新设备动作、批量下载和周期计划需另行明确。

保留已有任务状态及回执。重启、切换供应商或恢复旧版本都不能用新 ID 重放未知工作。

## 5. 失败与回退

停止新派发，保留错误、用量回执和未知操作状态，再修复配置或失败能力。回退需要匹配的旧代码、环境和停服备份，不只替换 TOML；恢复数据库前先核对外部副作用，不自动重启有已知失控行为的历史执行器。

`state/release-state.json` 在业务打开存储前原子记录内核及已启用插件的最高使用版本，启动健康后才更新上次成功运行记录。失败启动不覆盖上次成功记录；关闭插件不删除其最高版本记录。内核或插件降级、格式不一致、记录损坏均阻止业务启动，独立管理页继续可用。不要删改该记录绕过保护。

本轮没有更改业务数据格式，`release.json` 中的数据格式代号为 1；未来格式变化必须提供独立迁移程序及备份／回滚验收，否则拒绝自动启动。旧实例没有记录时显示未跟踪状态，首轮升级必须先停服备份；首次运行建立记录，不清空业务数据。`0.3.0` 之前的旧程序不认识此保护，回退到它们仍必须恢复匹配的完整备份，不能只替换安装包。

当前交互式 MCP OAuth 尚未实现；使用已支持的 stdio 或 HTTP 凭据方式并验证连接，不能以临时登录代替实例级凭据生命周期。认证和供应商限制详见[模型](../../src/assistant_runtime/core/models/README.md)与[MCP 模块](../../src/assistant_runtime/core/integrations/README.md)。

### 0.4.0 受控执行候选

公共执行的补充／回答新增必填 message_id，并返回持久消息回执，故公共 API 升至 2。内置扩展不调用这两个旧入口，按新 API 重新检查声明和依赖；外部插件需实际适配后升级。新增表不重置旧数据，data_format 仍为 1；核心版本保护阻止直接降级。受控能力、部署条件及未实测范围见[接入指南](controlled-execution.md)。候选源码和合成模型通过不等于生产发布或供应商验收。


### 0.4.9 模型请求可靠性

复用 Pi 1.4.0 的原生请求重试函数，统一主对话、任务、辅助推理、记忆与压缩的
逐次用量准入、结算、错误分类和共享总期限。默认临时错误额外尝试两次，未知错误
最多一次；确定的认证、余额和配额错误不原样重试，部分输出与未知操作不自动重发。
结构化错误贯通 IPC、MCP、执行记录与网页；安全恢复关联原失败执行和原预算。
未知费用保留预留，未确认操作仍受保护。API 2、data_format 1 不变，配置和存储为
增量调整。Web 1.2.3 使用新的失败展示和恢复入口，要求内核至少 0.4.9。
